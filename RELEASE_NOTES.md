# Sarex Loader v0.1.0-rc.6

Кандидат для приёмки: рабочие `-load sk/vk` подключены с отдельным подтверждением плана. Создание папок отключено. В ходе разработки реальных отправок и изменений Sarex не выполнялось.

- Исправлен WinError 32: тестовое читающее SQLite-соединение теперь явно закрывается. Защита рабочего журнала не ослаблена.
- BAT в ZIP всегда записывается с CRLF, включая сборку из GitHub REST blobs без checkout.
- Потоковое чтение PDF и проверка исходников перенесены на нативные Windows handles.
- `-test-pdf`, preview, fill и рабочий load используют общие проверки и SQLite.
- Постоянный рабочий журнал исключает повторную отправку после смены папки отчёта. Неопределённые операции требуют ручной сверки.
- Рабочая загрузка записывает GET-подтверждённые URL в переданный Excel; при ошибке сохранения повторный запуск восстанавливает URL без повторного upload.

Нативные результаты этого выпуска следует брать из последнего зелёного workflow **Windows and macOS validation** на том же коммите. CI не получает account.toml, историю Git, клиентские PDF/Excel и не обращается к Sarex.

## Передача и релиз

1. Убедиться, что Windows, macOS и compare зелёные для нужного коммита.
2. Скачать из артефактов этого запуска ZIP `…-windows.zip` и `…-macos.zip`; внутри есть README, инструкция приёмки, запускаторы и пустой образец учётной записи.
3. GitHub → Releases → Draft a new release → создать тег `v0.1.0-rc.6` **от проверенного коммита**. Название: `Sarex Loader v0.1.0-rc.6 — приёмка Windows и macOS`. Приложить оба ZIP, отметить Pre-release до решения заказчика.
4. Заказчик устанавливает Python 3.11+, распаковывает архив и начинает с `start.bat -help` на Windows. Все следующие действия — в README в порядке проверки.

Текст релиза:

> Проверка PDF, восстановление URL и загрузка СК/ВК. Windows/macOS: запуск через готовые скрипты. Рабочая загрузка выполняется только после подтверждения плана; dry-run не меняет Sarex и исходные файлы. Синтетический 99-Тест изолирован от рабочих разделов. Создание папок отключено. Не удаляйте SQLite и резервные копии; OUTCOME_UNKNOWN требует сверки. Учётная запись задаётся один раз через -setup. Первый запуск требует интернет для установки зависимостей.

Окончательный релиз 0.1.0 выпускается после приёмки согласованных сценариев заказчиком. Pre-release означает незавершённую приёмку, а не скрытую блокировку команд.

GitHub → Releases → Draft a new release → Choose a tag → создайте `v0.1.0-rc.5` от проверенного коммита main. Заголовок: `Sarex Loader v0.1.0-rc.5 — предварительная проверка`. Прикрепите оба ZIP и файл SHA256SUMS.txt, отметьте **Set as a pre-release**. Проверьте приватность репозитория перед Publish release. Это не финальная рабочая версия.

Производственная загрузка и создание папок выключены. Для проверки fill используйте копию Excel. Windows: результат ручного CI укажите после его завершения; полная загрузка на Windows ещё не принята. Установите Python 3.11+, распакуйте прикреплённый клиентский ZIP, откройте README и выполните настройку авторизации. Первый запуск требует интернет для установки зависимостей. ## Что изменилось в rc.2

- Автоматическая папка отчётов в Downloads; настройка `results_dir`.
- Сводка Markdown, CSV и журнал вместо длинного консольного вывода; технические данные в ZIP после успешного завершения.
- Команда `-test-pdf`: безопасная подготовка одного синтетического PDF, отдельные `--send SHA256` и подтверждение; цель только 7915046. Проверено mocks, реальной отправки новой командой не было.
- Отдельные архивы macOS и Windows. Windows-архив предварительный: полная отправка PDF там заблокирована, нативный CI ещё нужно выполнить.
- Авторизация в обоих архивах пустая. При первом запуске нужен логин и скрытый ввод пароля. Python 3.11+ и интернет для установки зависимостей обязательны. Это ZIP исходников с запускателем, не самостоятельный exe/app.

После зелёного Windows CI можно взять проверенный Windows ZIP из артефакта `validation-windows-latest`; macOS ZIP — из `validation-macos-latest`. Это предпочтительнее публикации Windows-архива до нативной проверки.

## Исправление Windows CI — rc.3

- Русская справка и ошибки выводятся в UTF-8 даже при перенаправлении в cp1252; это было причиной падения Windows runner.
- Проверяются все входные команды справки с cp1252, ASCII и UTF-8.
- Исправлена маршрутизация `python -m sarex_loader -test-pdf`.
- Actions обновлены для Node.js 24; журнал задания создаётся до установки, вывод CLI сохраняется при сбое.
- Нужен новый Run workflow после push. Re-run старого запуска использует прежний коммит. До зелёного Windows runner новая версия остаётся предварительной; полная Windows-загрузка всё ещё выключена и требует отдельной доработки и приёмки.

## Исправление сопоставления Windows — rc.4

- Вместо `DirEntry.stat()` используются свежие метаданные `os.stat(..., follow_symlinks=False)`: нулевые Windows ID больше не превращают разные PDF в ложные дубликаты. Настоящие hard-link дубликаты по-прежнему выявляются.
- Независимые проверки CI выполняются даже после отказа соседнего шага; при сбое сопоставления сохраняются фактические статусы и причины.
- Добавлена инструкция приёмки ACCEPTANCE.md. Пользователь сообщил об успешной отправке нового синтетического теста в 99-Тест; новых серверных операций в этом исправлении нет.
- Нативный Windows-прогон исправленной версии ещё требуется. Производственная загрузка и создание папок не включены.

## Исправления Windows CI — rc.5

- SQLite: владелец служебного файла может совпадать с реальным `TokenOwner` процесса, в том числе Administrators у повышенного runner. Это не отменяет закрытый ACL: доступ разрешён только пользователю, SYSTEM и Administrators. Чужой владелец и лишние разрешения по-прежнему блокируются. Существующие ACL и журналы не переписываются. Основание: [Microsoft: владелец нового объекта](https://learn.microsoft.com/en-us/windows/win32/secauthz/owner-of-a-new-object).
- Удержание папок Windows теперь запрашивает `FILE_LIST_DIRECTORY` вместе с атрибутами и не разрешает `FILE_SHARE_DELETE`. Одних запросов атрибутов недостаточно для требуемого участия в проверке совместного доступа: [Microsoft CreateFile](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-createfilea).
- BAT сначала использует установленный Python из `.venv`, затем Python из PATH, затем `py`. Пауза — только при запуске без аргументов. CI проверяет первый запуск BAT из нового архива и повторный запуск; stdout/stderr и код завершения сохраняются отдельно. Предыдущий лог не содержал вывода BAT, поэтому подтверждение исправления требует нативного прогона.
- `-load sk --dry-run` и `-load vk --dry-run` выполняют тот же безопасный просмотр, что `-preview`: GET и отчёты, без отправки, перемещения PDF и изменений Excel.
- Рабочие `-load sk/vk` без `--dry-run` и тестовая отправка на Windows ещё заблокированы. Этот выпуск исправляет обнаруженные ошибки CI, но не является завершённым переносом всей цепочки upload на Windows.
